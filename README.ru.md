## Ключевые понятия

- **Иерархия BR / SR / TR** — бизнес-, системные и задачные требования; TR живёт в трекере (цель + критерии приёмки), не отдельным файлом
- **Артефакт ADAPT** — реактивный двусторонний мост между неизменяемым ТЗ и BR/SR/SPEC; прямая интерпретация + обратные находки с двойной подписью (клиент + архитектор)
- **12 типов SPEC (закрытый список)** — ARCH / API / DATA / INT / PROC / UI / AI / SEC / OPS / TEST / DOC / UC — параллельная ось к требованиям через рёбра `constrained-by[]`
- **Комплект описания** — BR / SR / SPEC / TC-нормы утверждаются, версионируются и верифицируются вместе, как версия комплекта; на каждое утверждение — пара TC-норм (positive + negative)
- **Тест-кейсы (TC) как полноценные артефакты** — pos/neg-парность, VLM-judge для UX, типы TC по видам SPEC
- **Независимость от носителя V1–V6** — нормативный язык применим к любому носителю (git, документные хранилища, Mercurial, SVN отображаются на одни и те же возможности)
- **5 уровней зрелости RENAR** — RENAR-1 (начальный) → RENAR-5 (оптимизирующий); одна из осей общей зрелости SENAR

## Кому это нужно

- Командам, внедряющим SENAR, которым нужны нормативные правила для области требований
- Архитекторам и техлидам, проектирующим жизненный цикл требований на любом версионируемом носителе
- AI-инженерам, создающим агентов, которые порождают или меняют артефакты требований
- PM, юристам и аудиторам, которым нужны прослеживаемость и доказательства соответствия
